🎯 BayanWin

Lottery Prediction System - Software Documentation & Architecture

📋 System Overview

BayanWin is a modern, full-stack web application that predicts lottery numbers using multiple machine learning models. The system scrapes historical lottery data from Google Sheets (with optional incremental sync and full reconcile), can merge supplemental rows from Apify actors when configured, stores everything in InstantDB (Backend-as-a-Service), and runs six core ML predictors plus an optional Miro LLM meta-strategy that synthesizes a final pick from model outputs. An optional LLM “council” can produce an advisory report, and the API exposes D3-powered graph data (co-occurrence, Markov edges, Sankey).

Key Capabilities: The system supports 5 lottery games (Ultra Lotto 6/58, Grand Lotto 6/55, Super Lotto 6/49, Mega Lotto 6/45, and Lotto 6/42) and provides real-time predictions, statistical analysis, error distance tracking, Gaussian distribution visualization, graph analytics endpoints for the frontend, and lightweight per-user memory hooks for council context.

🏗️ System Architecture

BayanWin follows a three-tier architecture with clear separation of concerns:

Frontend Layer

  • React 18
  • Vite (Build Tool)
  • Tailwind CSS
  • Axios (HTTP Client)
  • Recharts (charts)
  • D3.js (graph visualizations)

Backend Layer

  • FastAPI (Python)
  • Uvicorn (ASGI Server)
  • 6 core ML models + optional Miro (LLM)
  • Google Sheets scraper (CSV / gspread incremental)
  • Optional Apify ingest & webhooks
  • Node.js bridge (InstantDB Admin SDK)

Data Layer

  • InstantDB (BaaS)
  • Google Sheets (Data Source)
  • REST API (Reads)
  • Admin SDK (Writes)

🔄 System Workflow Flowchart

The following flowchart illustrates the complete data flow and processing pipeline of the BayanWin system:

Flow Explanation:
  1. User Interaction: User selects a game type, which automatically triggers data scraping
  2. Data Collection: System scrapes latest data from Google Sheets, validates it, and saves to InstantDB
  3. Prediction Generation: User clicks “Generate Predictions” → historical data is loaded → six core models run with timeouts (thread pool) → Miro (optional LLM swarm) may add a synthesized pick → optional council report if requested and LLM_API_KEY is set
  4. Data Storage: All model picks (including Miro) are saved to InstantDB for history and accuracy tracking
  5. Analysis & Display: Predictions are displayed, accuracy is auto-calculated, and statistics/analysis are shown
  6. DRL Learning Loop: DRL agent receives feedback from accuracy calculations to improve future predictions

Stage-by-stage workflow (with code references)

Each stage maps to the actual code so you can trace requests end-to-end.

Stage 1: User selects a game → Auto-scrape

  • Frontend: frontend/src/App.jsx — handleGameSelect(gameType) runs when the user picks a game. It calls scrapeData({ game_type: gameType }) from frontend/src/services/api.js.
  • API call: api.js uses Axios with API_BASE_URL from frontend/src/utils/constants.js (default http://localhost:5000). Request: POST /api/scrape with body { game_type, full_sync }. Query ?full_sync=true forces a full CSV reconcile and resets the sheet cursor. Omitted game_type scrapes all configured games.
  • Backend: backend/app.py — @app.post("/api/scrape"). It builds GoogleSheetsScraper() from backend/scrapers/google_sheets_scraper.py, then scrape_game(..., full_sync=...) or scrape_all_games(full_sync=...). Writes go through backend/services/instantdb_client.py / Node scripts (e.g. save_results.js). When Apify is configured, a successful scrape may also run automatic actor ingest; the JSON response can include apify_ingest and a combined message (Sheets + Apify counts).
  • After scrape: If new results were added, the backend runs auto_calculate_accuracy_for_new_results() and may trigger DRL learning. Response includes success, stats, full_sync, message, and optional apify_ingest.

Stage 2: User clicks “Generate Predictions”

  • Frontend: App.jsx — handleGeneratePredictions() calls generatePredictions(selectedGame) → POST /api/predict/{game_type}. Optional query ?include_council=true asks the backend to attach an LLM council report to the same response (requires API key and council enabled).
  • Backend: app.py — @app.post("/api/predict/{game_type}"). Iterates six core entries in model_types (XGBoost, DecisionTree, MarkovChain, AnomalyDetection, NashHotFilter, DRL). Each runs model_instance.predict(game_type) in a ThreadPoolExecutor (60s per model, 120s for DRL). Then, if MIRO_STRATEGY_ENABLED and LLM_API_KEY are set, run_miro_strategy_predict in backend/services/miro_strategy.py runs in a separate pool with up to ~180s timeout; the Miro pick is stored like other models. If the key is missing or Miro is disabled, predictions still contains a Miro entry with an explanatory error string for the UI.
  • Saving: Each successful prediction is stored with instantdb.create_prediction(game_type, prediction_data). A background thread runs auto_calculate_accuracy_for_new_results(game_type).
  • Response: { success, game_type, target_draw_date, predictions, timestamp } plus optional council_report. predictions includes core models and Miro. Frontend maps these into PredictionDisplay (core grid + Miro panel).

Stage 3: Viewing results, stats, and accuracy

  • Historical results: HistoricalResults → getResults(gameType, page, limit) → GET /api/results/{game_type}. Backend: @app.get("/api/results/{game_type}") (line ~96) uses instantdb.get_results(...).
  • Statistics: StatisticsPanel → getStatistics(gameType) → GET /api/stats/{game_type}. Backend uses utils/frequency_analysis.py (e.g. get_hot_numbers, get_cold_numbers, get_overdue_numbers).
  • Error distance: ErrorDistanceAnalysis → getPredictionAccuracy(gameType) → GET /api/predictions/{game_type}/accuracy. Backend uses instantdb.get_prediction_accuracy() and utils/error_distance_calculator.py.
  • Gaussian: getGaussianDistribution(gameType) → GET /api/stats/{game_type}/gaussian; backend returns sum/product data for the scatter plot.
  • Graph analytics (D3): Co-occurrence pairs GET /api/graphs/{game_type}/cooccurrence, directed Markov-style edges GET /api/graphs/{game_type}/markov-edges, and Sankey-style model-vs-hot breakdown POST /api/graphs/{game_type}/sankey with the current predictions map in the body.
  • Council report (standalone): POST /api/predict/{game_type}/council-report with optional user_key to merge persisted memory into the prompt; can load latest predictions from DB when use_latest is true.

CORS middleware and frontend–backend connection

Why CORS matters: The React app runs at http://localhost:3000 and the API at http://localhost:5000. Browsers enforce the same-origin policy; a request from the frontend to the backend is cross-origin, so the backend must send CORS headers for the browser to accept the response.

Backend CORS (FastAPI): In backend/app.py, right after creating the FastAPI app (lines 50–56), the app adds CORSMiddleware:

  • allow_origins=["*"] — any origin (e.g. http://localhost:3000) can call the API. In production you should restrict this to your frontend origin(s).
  • allow_credentials=True — allows cookies/credentials if used later.
  • allow_methods=["*"] and allow_headers=["*"] — all usual HTTP methods and headers are allowed.

Every response from FastAPI therefore includes CORS headers that tell the browser the cross-origin response is allowed.

Development proxy: In frontend/vite.config.js, requests to path /api are proxied to http://localhost:5000. When using this proxy, the browser only talks to the Vite server (same origin); Vite forwards /api/* to the backend, so CORS is less visible. If the frontend is configured to call http://localhost:5000 directly (e.g. API_BASE_URL = 'http://localhost:5000' in constants.js), then the backend CORS middleware is what allows those cross-origin requests to succeed.

🤖 Machine Learning Models

BayanWin runs six trainable / algorithmic predictors on every generation, then optionally adds Miro—an LLM-driven meta-layer that reads those outputs and produces a single synthesized line (stored as model_type: "Miro"). Configure via environment variables such as LLM_API_KEY, MIRO_STRATEGY_ENABLED, and LLM_COUNCIL_ENABLED.

1. XGBoost Model

Type: Gradient Boosting

Approach: Uses historical patterns and gradient boosting trees to identify complex relationships in lottery number sequences.

Performance: ~6-10 seconds per prediction

2. Decision Tree Model

Type: Random Forest + structured features

Approach: Rich feature vectors (deltas, Markovian transitions, stats), K-Means clustering for localized behavior, PCA where used, and Monte Carlo sampling with sum guard rails—see backend/ml_models/decision_tree.py.

Performance: ~4-6 seconds per prediction

3. Markov Chain Model

Type: State Transition Model

Approach: Models number sequences as state transitions, predicting next numbers based on transition probabilities from historical data.

Performance: ~1-3 seconds per prediction

4. Anomaly Detection Model

Type: Monte Carlo / Gaussian (Sum/Product) Distribution Analysis

Approach: Uses sum and product of drawn numbers; vectorized Monte Carlo and Gaussian mixture to select numbers in high-probability regions.

Performance: ~0.5-3 seconds per prediction

5. NashHotFilter

Type: Nash Equilibrium + Hot-Number Filter

Approach: Smart wheel with Nash mixed-strategy (8 tickets, 12.5% each) and hot-number probability filter; enforces 3-even/3-odd balance. Hybrid mode replaces cold numbers with hot alternatives.

Performance: Instant (no training)

6. Deep Reinforcement Learning (DRL)

Type: Reinforcement Learning Agent

Approach: Uses deep neural networks with 3 feedback loops. Learns from accuracy records to optimize predictions over time (5 episodes per prediction).

Performance: ~20-40 seconds per prediction

Special Feature: Continuously improves through feedback loop from accuracy calculations

7. Miro (LLM meta-strategy)

Type: Multi-agent LLM synthesis (not a classical ML trainer)

Approach: Runs after the six core models, consumes their numeric outputs, and returns a single six-number pick; persisted like other predictions. Uses a small number of LLM calls per run; server-side timeout up to ~180 seconds.

Performance: Seconds to a few minutes, bounded by provider latency and timeout

Related: Optional LLM council advisory report (agreement, outliers, caveats)—either bundled via ?include_council=true on predict or via POST /api/predict/.../council-report.

📊 Data Flow & Storage

Data Sources

  • Google Sheets: Primary source. Supports incremental pulls (e.g. gspread when credentials exist) and full_sync full CSV reconcile with cursor reset.
  • Apify (optional): When APIFY_API_TOKEN and an actor are configured, the backend can poll datasets (POST /api/ingest/apify), accept run-finished webhooks (POST /api/webhooks/apify), and optionally auto-ingest after a successful Sheets scrape—all deduped and additive to InstantDB.
  • InstantDB: Backend-as-a-Service database storing all results, predictions, accuracy records, and small optional user-memory blobs for council context.

Data Operations

Operation Method Description
Read Results REST API FastAPI backend queries InstantDB via REST API for reads and queries
Write Results Node.js Admin SDK Reliable write operations using Node.js bridge scripts with InstantDB Admin SDK
Write Predictions Node.js Admin SDK All predictions saved via Admin SDK bridge for consistency
Auto-Calculate Accuracy REST API + Admin SDK Matches predictions to results and calculates error distance metrics

🔌 Main API Endpoints

Game Management

  • GET /api/games - List all available games

Results & Data

  • GET /api/results/{game_type} - Get historical results (paginated)
  • POST /api/scrape - Scrape Google Sheets (body: optional game_type, full_sync; query full_sync=true overrides). Response may include apify_ingest when auto-ingest runs.
  • POST /api/ingest/apify - Poll an Apify run dataset and merge normalized rows into InstantDB
  • POST /api/webhooks/apify - Webhook for finished Apify runs (optional X-Webhook-Secret when configured)

Predictions

  • POST /api/predict/{game_type} - Run six core ML models, then Miro when enabled; query include_council for optional LLM advisory report in the same response
  • POST /api/predict/{game_type}/council-report - Standalone LLM council summary (body: predictions map and/or use_latest, optional user_key)
  • GET /api/predictions/{game_type} - Get stored predictions
  • GET /api/predictions/{game_type}/accuracy - Get prediction accuracy metrics
  • POST /api/predictions/{prediction_id}/calculate-accuracy - Calculate accuracy for a prediction

Statistics

  • GET /api/stats/{game_type} - Get frequency statistics (hot/cold/overdue numbers)
  • GET /api/stats/{game_type}/gaussian - Get Gaussian distribution analysis

Graphs (D3 / analytics)

  • GET /api/graphs/{game_type}/cooccurrence - Pair co-occurrence counts within draws
  • GET /api/graphs/{game_type}/markov-edges - Directed transitions between consecutive draws
  • POST /api/graphs/{game_type}/sankey - Hot vs “other” counts from a current predictions map (JSON body)

Accuracy & diagnostics

  • GET /api/accuracy/diagnostics/{game_type} - Counts, date ranges, and matching hints for debugging
  • POST /api/accuracy/auto-calculate - Manually trigger batch accuracy matching (optional game_type in body; all games if omitted)

User memory (optional)

  • GET /api/memory/user/{user_key} - Read persisted preferences / summary stub for a client key
  • POST /api/memory/user - Upsert pinned games, preferences, or last council summary snippet

System

  • GET /api/health - API health check
  • OpenAPI: Interactive docs at http://localhost:5000/docs when the backend is running

⚙️ Technical Implementation Details

Backend Architecture

The FastAPI backend serves as the central orchestrator, handling all business logic, ML model coordination, and data operations. It uses:

  • Async/Await: Non-blocking operations for better performance
  • CORS Middleware: Enables frontend-backend communication
  • Pydantic Models: Request/response validation
  • Concurrent Processing: ML models run with timeout protection
  • Background Tasks: Auto-calculation of accuracy runs asynchronously

Development Ports

Backend runs at http://localhost:5000 (Uvicorn). Frontend runs at http://localhost:3000 (Vite; port set in vite.config.js) and proxies /api to the backend.

Frontend Architecture

The React frontend provides a modern, responsive user interface:

  • Component-Based: Modular React components for maintainability
  • State Management: React hooks for local state management
  • Real-time Updates: Immediate display of predictions as models complete
  • Error Handling: Graceful error states and user feedback
  • Visualizations: Recharts for charts; D3 for network/Sankey-style graphs fed by /api/graphs/...

Database Schema

InstantDB stores three main entity types:

  • Results: Historical lottery draw results (draw_date, numbers, jackpot, winners)
  • Predictions: Per-model rows (including Miro), six predicted numbers, target draw date, optional prior-prediction history fields
  • Accuracy Records: Prediction accuracy metrics (error_distance, numbers_matched, distance_metrics)
  • User memory (if used): Small JSON records keyed for council personalization (not required for core predictions)
